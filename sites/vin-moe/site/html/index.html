How this site runs

This site is a static page served by nginx from a single-node Kubernetes cluster on dedicated hardware. One repository defines the cluster, the container image and the Deployment, in about 8,000 lines of Terraform that HCP Terraform applies. The repository is the source of truth: changes are made there and applied from there, never against the cluster by hand.

The sections below follow one change from a commit to a running pod, and describe the platform it lands on.

AI wrote the HTML/CSS on this page. I do infrastructure, not frontend.

the cluster

  1. the node

    Talos Linux runs on dedicated hardware. It has no shell, no SSH and no package manager, so every change is a declarative machine config applied over an mTLS API. The ephemeral and state partitions use LUKS2. Boot media comes from an Image Factory schematic pinned by content hash, and the installer image uses that same schematic. Point it at the stock image instead and Talos removes every system extension when it writes to disk.

  2. control plane

    The cluster is one node running both the control plane and workloads, with scheduling on control-plane nodes enabled. Terraform generates the machine secrets, applies the config, bootstraps etcd and keeps the resulting kubeconfig in state.

  3. networking

    Cilium provides the CNI and enforces NetworkPolicy in eBPF. Its policies select workload identities rather than only CIDR blocks, which allows a rule to match the node's own host identity. Hubble serves the flow data behind single sign-on.

  4. storage

    local-path is the only storage class. It provisions a host-path volume per pod. One node has no second failure domain, so a replicated pool would not add durability.

ingress and dns

  1. ingress and certificates

    ingress-nginx runs as a DaemonSet on the host network, bound to the node's public IP. There is no load balancer. cert-manager holds one ClusterIssuer per domain and solves DNS-01 challenges against Cloudflare. Every zone uses strict SSL, so TLS is validated independently on both hops: browser to Cloudflare, and Cloudflare to the origin.

  2. dns and cdn

    A proxied Cloudflare A record points at the node. Because certificates are issued over DNS-01, no ACME validation traffic reaches the origin. A Terraform-managed cache ruleset caches every response on this hostname, HTML included, so most requests never reach the cluster.

the image

  1. the registry

    Images live in GitLab's own container registry, which runs on the same cluster at artifacts.vinnel.cloud, one repository per site. Pods authenticate with a project deploy token mounted as an imagePullSecret rather than a personal one. Base images arrive through a pull-through cache at mirror.vinnel.cloud, so a rebuild does not re-fetch Alpine from Docker Hub against the node's shared anonymous rate limit.

  2. build stages

    The image builds in four stages, each base pinned by digest. The first converts the source PNG into a multi-resolution .ico and an apple-touch icon, and squares the avatar down to a 288-pixel WebP. The second compiles ngx_brotli against the exact nginx version in the base image, because upstream publishes no compatible release. The third builds the assets. The fourth is nginx-unprivileged and runs as a non-root user.

  3. assets

    The web font is downloaded during the build and served from this origin, and the avatar is committed rather than hotlinked, so nothing third-party loads at runtime and the Content-Security-Policy stays at default-src 'self'. CSS and JavaScript are minified and renamed to include a hash of their contents, with every reference rewritten to match; that hash is what the one-year immutable cache header applies to. Text files are compressed once at build time with gzip -9 and brotli -q 11.

serving

  1. nginx

    nginx serves the pre-compressed files directly, so it never compresses a response per request. Hashed assets get immutable cache headers and open_file_cache keeps hot file descriptors open. Every response carries HSTS, CSP, nosniff, frame and referrer policy headers. /healthz returns plain text for the probes, .html URLs redirect to their extensionless form, and the old /posts/ addresses redirect to their new home on blog.vin.moe. The same pods answer both hostnames: one server block per host, with the blog host serving only the reader page, its stylesheet, and the public post endpoints.

  2. the page

    The page uses no framework and no bundler. The font and the avatar are the only requests besides the stylesheet and script until you open the blog. One palette covers both themes through light-dark(), so the toggle changes a single property, and the section numbers are a CSS counter. The tabs are an ARIA tablist with arrow-key navigation and fragment links, animated by the View Transitions API where it exists. Posts render into details elements for inline reading, and each one opens full screen on blog.vin.moe under its own shareable fragment, rendered there from the same posts.json the tab loads. With JavaScript disabled the tab bar is hidden and every panel renders, except the blog, which points at the feed instead.

  3. the deployment

    Two replicas sit behind a ClusterIP Service. Each requests 50m CPU and 16Mi of memory, with limits of 200m and 64Mi. Containers run as non-root with all capabilities dropped, no privilege escalation and the RuntimeDefault seccomp profile. Startup, readiness and liveness probes call /healthz. Rollouts surge to 100% with zero unavailable pods and a pre-stop drain, a PodDisruptionBudget keeps one replica serving, and a VerticalPodAutoscaler adjusts memory within that band.

posts

  1. writing and reading

    Posts are written in an editor at admin.vinnel.cloud, behind the same single sign-on as everything else, and stored on a volume beside it. The blog tab requests /posts.json, nginx proxies that path to the editor over the cluster network, and the markdown is rendered there rather than at build time. A new post therefore appears without rebuilding or redeploying anything.

  2. the durable copy

    Publishing also commits the markdown to the integration branch through the GitLab API, and CI opens the merge request. The repository keeps the durable copy and the volume serves the live one. Each write purges the four affected URLs at the edge, plus the post's own page, so the blog stays cached and still shows the change within about a second.

deploying a change

  1. validation

    A merge request that touches a site runs the shared build-script test suite against a synthetic page, which covers the asset-hashing and cache-busting logic every site's build.sh has in common. Writing a post skips all of it, because a post is no longer part of the image. The infrastructure plan skips the paths Terraform does not read, so editing HTML does not queue an apply on the node that also serves the page.

  2. build and digest

    buildctl pushes the :latest and commit-SHA tags against a registry-hosted layer cache, so unchanged stages, including the compiled nginx module, are pulled rather than rebuilt. The sha256 digest it returns, not the mutable tag, is merged into a shared image manifest and committed by the job that built it. On a push race the retry re-merges onto whatever landed first: two sites deploying at once write neighbouring lines of the same JSON file, and a rebase would hit the same conflict on every attempt.

  3. rollout

    The rollout reads the digest back from git at the remote tip, so it deploys what was recorded rather than what a job variable held. It sets the image to that exact digest and waits on the rollout status. Cloudflare's cache is purged once the new pods are serving; purging first would re-cache the outgoing build.

  4. reconcile and mirror

    terraform apply needs only the digest-recording step, not the rollout. Both read the same committed manifest, so the imperative rollout and the declarative apply converge on the same image reference whichever finishes first. Commits authored by CI push with the project's job token, which GitLab excludes from triggering a pipeline, and carry a [skip ci] marker as well. A final job pushes the site source to a public GitHub repository through a scoped token, committing only when something changed.

ci runners

  1. the runners

    Two gitlab-runner Deployments run in the cluster, both using the Kubernetes executor, neither sharing a Docker socket. One takes untagged jobs at a concurrency of 4. The other takes only jobs tagged privileged-build, so an ordinary lint or test job cannot land on a pod running privileged. Each job gets its own pod built from the image it declares, and no daemon survives between jobs. The runner config is a Secret, and a config-hash annotation restarts the Deployment when it changes.

  2. the runner image

    The runner image is built on debian:trixie-slim, pinned by digest, with the toolchain baked in: node, gh, jq, rsync, kubectl, tflint, shellcheck, yamllint and build-essential. It carries nothing a pipeline does not run, because every extra binary is more vulnerability surface for the nightly scan to trip over. Pods pull it on every start. With one node and a mutable :latest tag, the kubelet would otherwise keep the first copy it pulled and ignore later rebuilds, including the ones the vulnerability scan triggers. Because that tag decides what CI runs, a rebuild is smoke-tested before it is allowed to become :latest.

  3. registry access from jobs

    registry.vinnel.cloud stays behind the Cloudflare proxy for public traffic, but the proxy's request-body limit is smaller than the runner image's base layer. A hostAliases entry routing to the node's ingress lives on the runner's executor config rather than on individual jobs, so every job pod inherits it, paired with a firewall rule that opens the web ports to the pod network.

observability

  1. signoz

    SigNoz stores metrics, logs and traces in ClickHouse. An OpenTelemetry collector discovers targets by pod annotation, so a new workload becomes observable by adding two labels, with no scrape config to edit. ingress-nginx exports OTLP spans, so a slow request and the logs behind it belong to one trace.

  2. alerting

    Alert rules are Terraform resources rather than clicks in an interface: node NotReady, PVC above 85%, certificate expiring within 14 days, and workload below desired replicas. They notify Slack and renotify every four hours while still firing, and dashboards go through the same API. A node that stops responding also stops alerting, so that check cannot live here: Better Stack polls from outside, and status.vinnel.cloud frames its status page.

resilience

  1. failure testing

    Chaos Mesh deletes a random site pod every 30 minutes and stresses one hourly, which exercises the disruption budget and the probes above against real failures rather than assumptions. It is scoped to the per-site namespaces, and never touches authentication, the mesh, or the alerting meant to catch problems.

  2. backups

    Velero takes two filesystem backups a night, one offsite at 03:00 and one into the cluster's own object store at 03:30, both expiring after seven days. restic snapshots the volumes separately, encrypted and deduplicated on the client so the bucket holds only ciphertext, keeping seven daily snapshots and running an integrity check each time.

security

  1. the firewall

    The Talos host firewall defaults to deny. Ports 80 and 443 accept only Cloudflare's published edge ranges, so scans against the origin IP are dropped before nginx sees them. The Kubernetes and Talos APIs stay reachable on purpose: both are certificate-gated with no password surface, CI and Terraform have no fixed egress addresses to allow, and the Talos API is the recovery path for the firewall itself.

  2. access

    Admin interfaces sit behind Authelia two-factor authentication. The development machine is reachable only over a self-hosted WireGuard mesh, never the public internet. Secrets are generated by Terraform and held in state, never in the repository. CI authenticates with a token scoped to patching Deployments in one namespace. Workloads run under Pod Security Standards, except the runner pods, which need privileged mode for Docker-in-Docker and are separated from ordinary jobs by runner tag. The public blog endpoints are the one unauthenticated path into a service that is otherwise behind single sign-on, so they are served from a route that only reads published posts and never reaches the editing API.

  3. supply chain

    Base images and Terraform providers are pinned by digest or lockfile, so moving a tag cannot change what ships. Every push runs go vet and the Go tests, shellcheck, yamllint, and gitleaks over the full history; terraform fmt and tflint run before the plan they gate. Grype scans the runner image on a schedule, and a high or critical finding triggers a rebuild. Renovate opens the version bumps, grouped so a dozen digest updates arrive as one merge request, and major updates wait for review.
